# TeeCircle v1 Defect Log (2026-07-18)

Single source of truth for the finalize-v1 release. Sources: static code audit
(`CODE-*`, this file's first section) and device audit (`DEV-*`, appended
during the device walk). Severity: P0 = crash / data loss / flow-blocking /
App Review rejection risk; P1 = works but bad experience; P2 = cosmetic.

| CODE-14 | P1 | Friends | src/hooks/useFriendships.ts:19-107 | Unlike `useRounds.ts` (153-179) and `useRoundResponses.ts` (84-99), this hook sets up no `postgres_changes` realtime subscription on the `friendships` table — it only fetches once on mount/user change. A friend request received or accepted by another user while this screen is open won't appear until the consumer explicitly calls `refresh()` or the hook remounts. | Subscribe to `friendships` rows involving the current user (`user_low`/`user_high`) and refetch on change, matching the pattern already used in `useRounds.ts`, so incoming/accepted requests update live. |
| CODE-15 | P2 | Rounds sync | src/hooks/useRounds.ts:153-159 | The `rounds` realtime channel filters `postgres_changes` on `table: 'rounds'` with `filter: created_by=eq.${user.id}` — only rows the user created. A non-creator participant isn't notified in realtime when the round itself changes (e.g. creator sets `status: 'locked'`); their copy only updates if their own `round_responses` row also changes, which a lock doesn't touch. | Also refetch when a round the user participates in (not just created) changes — e.g. subscribe without the `created_by` filter, or via a join/broader channel — so participants see status changes without a manual pull-to-refresh. |
| CODE-16 | P1 | Push notifications | src/hooks/usePushNotifications.ts:56-99 | The hook registers a push token on login/foreground but has no counterpart that runs on sign-out: `AuthContext.tsx`'s `signOut` (244-250) never deletes the device's `push_tokens` row. | CODE-17 | P0 | Account deletion | src/context/AuthContext.tsx:252-273 | `deleteProfile()` deletes app data via the `delete_user_account` RPC (confirmed real: friendships, group_members, round_responses, push_tokens, rounds, groups, profile — see `supabase/delete_user_rpc.sql`) and then calls `supabase.auth.signOut()` — but it never removes the underlying Supabase Auth identity (`auth.users` row / email+password credential / Apple-Google identity link), which requires an admin-privileged call the client can't make. The stub edge function `supabase/functions/delete-account-v1/` exists as an empty, untracked directory with no code in it, confirming no server-side endpoint performs this. After "deleting" their account, a user's login credential still works — they (or anyone with the password) can sign back in to a wiped-but-not-gone account. | Account deletion must also delete the Supabase Auth user (via a service-role edge function calling `supabase.auth.admin.deleteUser`), so the credential can no longer authenticate — required for Apple App Review (Guideline 5.1.1(v)) and to match the device-audit checklist's own expectation ("old credentials no longer sign in"). |
| CODE-18 | P1 | Auth / onboarding | src/context/AuthContext.tsx:135-139 | `ensureProfile()` is invoked fire-and-forget (`.catch(() => {})`) from both the session-init path (135-139) and the `onAuthStateChange` handler (184-185); any failure (network blip, upsert conflict) leaves `profile` permanently `null` with zero UI indication. `HomeScreen.tsx:64` only redirects to the username-claim screen `if (user && profile && !profile.username)` — since that condition requires `profile` to be truthy, a null profile never triggers the redirect, so the user is silently stuck on Home with no username and no way to discover or retry it. | On a profile-load/create failure, either retry with backoff and surface an error/retry UI, or make the username-onboarding gate also trigger on `profile === null` so the user isn't stranded silently. |

[]`, `?? null` fallbacks), then overwrites `player_handicap_profiles` with a handicap computed as if this were their first round ever. | Check all three `Promise.all` results for `.error` and abort (return `false`) if any failed, instead of silently treating a fetch error as "no existing data" and overwriting the stored handicap index. |
